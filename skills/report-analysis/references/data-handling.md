# Data access and version control are separate

Agents never open restricted content unless the project's AGENTS.md explicitly allows it for that source. Ask what data the project uses and where they are kept, so that agents and connected folders stay clear of them. The applicable BAA, DUA, institutional policy and repository restrictions determine what a project may allow; a BAA is not blanket authorization. Do not claim this plugin certifies compliance. Reuse established boundaries. Otherwise work from code, public documentation and independently synthetic examples.

Keep restricted inputs in a separate authorized folder outside the project where possible, reached only through the source's package configuration. An ignored data-raw/ directory inside the project is allowed but less preferred: an ignored folder is still readable, so any AI tool connected to the project folder can reach it, which makes access hard to manage unless the project's AGENTS.md permits agents that access for the source. If restricted data sit inside the project, do not connect that folder to an AI tool without that permission. Remind users that connecting a parent folder can expose its children to tools. An ignored directory remains readable to agents; .gitignore is not an access-control mechanism. Review copied code/startup/configuration before running it so it cannot silently load sensitive data or write into the original project. Do not upload data to another service just because local access is allowed.

The starter .gitignore ignores common data formats as a safety net, but file extensions cannot identify every sensitive file. Text, Markdown, images, HTML, logs and intermediate outputs may also contain restricted information. Review provenance and permitted disclosure before tracking or sharing anything; filename patterns are not proof of safety.

Adapt patterns deliberately. Keep approved public/synthetic fixtures outside wholly ignored data folders, with narrow exceptions such as !tests/fixtures/synthetic.csv. If a parent directory is ignored, re-include the parent before child exceptions can work. Verify with git check-ignore --no-index -v and compare git ls-files metadata. Already tracked content stays tracked; ignore changes do not scrub history. Do not untrack, delete or rewrite history without the appropriate authorized remediation scope.

Whether `figures/` and `tables/` are tracked is asked during setup. When outputs require review before release (for example USRDS review before publication), they stay ignored until the governing review clears them; then remove the two lines from .gitignore and inspect the contents before staging. When outputs need no review, track them from the start. `docs/` is always tracked because it is the published site, so it never contains results from restricted data unless the review that AGENTS.md names has cleared those outputs for release. Apply each source's actual disclosure rules; do not universalize one study's small-cell threshold.

If restricted material is committed or pushed, stop, tell the person who holds the data agreement, and follow GitHub's guidance on removing sensitive data from a repository. Deleting the file in a new commit does not remove it from history or from forks.
