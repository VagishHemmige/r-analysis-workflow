# Efficient, resumable questionnaire

Initialization always includes a questionnaire. Inspect supplied context first, retain answers and ask one short decision at a time. Do not present this entire checklist as mandatory questions. If a user supplies the latest RMD, accept it as current and focus on what's missing.

1. What existing materials should inform this project? Invite files or pointers to a protocol/IRB, plan, R/RMD scripts, resources, pertinent papers and earlier results. Ask which are current only when unclear. Exclude patient records and credentials. In the AGENTS.md Data sources table, set "What AI agents may do" to "None: code, documentation and synthetic data only" for every restricted source, and do not offer or suggest allowing more.
2. What is the research goal and starting state: new work, existing folder, repository or mixed materials? Identify authoritative methods and unfinished scientific decisions from the materials.
3. Who makes the scientific decisions for this project, and in which areas? If the materials name investigators (for example the PI and co-investigators on an IRB protocol), suggest them with their areas for the person to confirm or change. Record the names in AGENTS.md. If no one is named yet, leave the line marked as still to be filled and say that decision issues can be drafted but not settled until it is.
4. What assistance is wanted: guided learning, review, editing/organization, execution? Distinguish local changes, Git commits/branches/PRs, external communications, installation and publication; reuse existing authorization.
5. Which data locations and access boundaries are approved? Clarify unknown restrictions; agents do not open sensitive files. Record references to policy, not secrets or patient data.
6. Retain existing organization or adopt the blueprint? Present concrete proposed moves/archives based on dependencies. Ask only about ambiguous active/superseded files. Preserve half-done RMD rationale.
7. Apply cosmo, Rcode callouts and docs/ for new Quarto work unless opted out; retain established alternatives. Establish permitted render execution. Assume a public repository on GitHub Free; if the person says it will be private, tell them that on GitHub Free a private repository has neither GitHub Pages nor branch rulesets. Inspect runtime readiness before proposing installation.
8. Do the figures and tables need review before they can be public? Ask this directly; do not infer it from the data sources. If yes (for example USRDS review before publication), `figures/` and `tables/` stay in .gitignore until that review clears them, and AGENTS.md names the review. If no, track them from the start. `docs/` is always tracked.
9. Review the rest of .gitignore explicitly: safe data exceptions and tracked-file hazards. Suggest useful references/ documents in Markdown.

Record completed steps and remaining questions in the existing tracker or an agreed setup note; personal permissions stay in private instructions. Resume without repeating settled choices. A setup proposal should be actionable, not an exhaustive inventory report. Do not demand more materials when existing ones suffice.
